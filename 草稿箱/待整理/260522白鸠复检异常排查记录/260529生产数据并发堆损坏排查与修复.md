## 1. 现场异常现象

### 1.1 崩溃信息

| 项 | 内容 |
|----|------|
| 程序 | `ElectroVision.exe` v3.0.5.11 |

|  fault 模块 | `ntdll.dll` |

| 崩溃时间（事件查看器） | 2026-05-28 21:46:20 |

### 1.2 调用堆栈（DMP）

调试器停在 Qt 释放字符串内存处，**崩溃点通常不是根因**，而是更早内存破坏的延迟爆发：

```text
ntdll.dll          RtlpHpHeapHandleError / RtlFreeHeap
ucrtbase.dll       _free_base
Qt5Core.dll        QTypedArrayData::deallocate          ← 当前停点
Qt5Core.dll        QString::operator=
Qt_Vision.dll      LocalFile::saveProductCsvFile        ← 约 134 行 xlsx.save()
Qt_Vision.dll      DataTransmission::saveFileData       ← 约 66 行
Qt_Vision.dll      Qt_Vision::slotTimeOut               ← 约 606 行
Qt5Core.dll        QTimer::timeout
```

### 1.3 触发时序

- `QTimer` 周期 **100ms**（`Qt_Vision.cpp` 约 117–120 行）。
- `timeout_3 == 50` 时约 **每 5 秒** 执行一次数据保存（`slotTimeOut` 约 592–605 行）：
  1. 可选 `saveDetailData()`（详细 NG 记录）
  2. `saveProductData(maxSpeed)`
  3. `saveFileData(0)` → `saveProductCsvFile` → **`xlsx.save()`**

## 2. 根因分析

### 2.1 共性结论

`0xC0000374` 在此路径上的直接诱因是：**多线程无锁并发访问 Qt 容器**（`QVariantMap` / `QQueue`），破坏堆元数据；在 `xlsx.save()` 内大量 `QString` 分配/释放时触发检测。

与汇总文档 **#9 参数导出 CSV** 为 **不同堆栈**（彼为 `ParameterExportTable::exportAll`），但属 **同类并发模式**。

### 2.2 问题 1：`getTotal` / `getNgTotal` 无锁读

| 线程 A（读） | 线程 B（写） |
|--------------|--------------|
| **GUI 主线程** | **`MainThread`（QThread，每路相机）** |
| `LocalFile.cpp:121-122` `getTotal` / `getNgTotal` | `MainThread.cpp:492` → `dealResultData` |
| 经 `DataTransmission::saveFileData` → `saveProductCsvFile` | `ProductDataHelper.cpp:87` 持 `dataLock`，内部 `setTotal` / `setNgTotal` |

**共享资源**：`productDataImpls[i]->Data`（`QVariantMap`）。

> 注释写「放置到主线程处理」，实际为 **`MainThread` 工作线程**，非 Qt GUI 主线程。

### 2.3 问题 2：`getDetailQueue` 无锁

| 线程 A（读） | 线程 B（写） |
|--------------|--------------|
| GUI：`LocalFile.cpp:277` `getDetailQueue()` | `MainThread`：`dealResultData` 内 `NgDetails.enqueue`（约 304 行） |
| copy + `clear()`，**无锁** | 在 `dataLock` 内写队列 |

**共享资源**：`ProductDataHelper::NgDetails`（`QQueue<NgDetail>`）。

与问题 1 在 **同一 `slotTimeOut` 周期**（599 行 `saveDetailData` + 605 行 `saveFileData`）相邻触发。

### 2.4 问题 3：`saveProductData` 无锁写盘

| 线程 A | 线程 B |
|--------|--------|
| GUI：`Qt_Vision.cpp:607` `saveProductData(maxSpeed)` | `MainThread`：`dealResultData` 写 `Data` |
| 循环 `productDataImpls[i]->saveSelf()`（磁盘 IO） | 持 `dataLock`（修复前 A 侧无锁） |

**共享资源**：同上 `Data`，以及 `RecrodBanciDate` / `RecrodBanCi`。

### 2.5 其它未纳入首轮修复的路径（第二轮已补）

| 数据 | 写路径 | 读/清路径 | 风险 |
|------|--------|-----------|------|
| `recheckResults` | `OutPutThread` → `dealRecheckResultData` | GUI 定时器直接 `recheckResults.dequeue()` | **高**（复检必走） |
| `camAlgorithmTimes` | `dealResultData`（`UseAnalysis=1`） | GUI `getCameraAlgorithm` / `clearCameraAlgorithm` | **中高** |
| `cameraDetectStatus` | `dealResultData` → `updateCameraDetectStatus` | `ModbusRtuSlave` 线程 `getCameraDetectStatus` | 中低（状态位错乱为主） |
| `camLedStatus` / `MergeLedStatus` | `dealResultData` | GUI `GetLedStatus`（已有锁）/ `ResetLed`（已补锁） | 中（卫品） |
| `camResults` 等 | `MergeCameraResult` | `SingleChip` → `ResetMergeData`（已补锁） | 低（封口+下位机计数） |

## 3. 修复方案与改动清单

### 3.1 锁策略

- **一把锁**：`QRecursiveMutex dataLock` 保护 `ProductDataHelper` 内所有生产相关共享状态。
- **读写对称**：凡读写 `Data`、`NgDetails`、`recheckResults`、`camAlgorithmTimes`、`cameraDetectStatus`、流水灯/合并数据的相关 public 接口均加锁。
- **嵌套安全**：`dealResultData` 外层持锁 + 内部 `setTotal` 等再次加锁 → 依赖递归互斥量。

### 3.2 文件级改动

#### `ProductDataHelper.h`

- `QMutex dataLock` → **`QRecursiveMutex dataLock`**
- `recheckResults` 移至 **private**
- 新增 **`bool tryDequeueRecheckResult(RecheckResultInfo& result)`**

#### `ProductDataHelper.cpp`

**读 `Data`（加锁）**

- `getTotal`、`getNgTotal`、`getAiNgCount`
- `getType`、`getTypeTotal(int)`、`getTypeTotal()`、`getLost`
- `getCamMultiRoad`、`getCamMultiTotal`、`getCamMultiNgTotal`
- `getRealTotal`、`getRealNG`、`getDefectNG`

**写 `Data`（加锁）**

- `setTotal`、`setNgTotal`、`setType`、`setLost`
- `addAiNgCount`、`addRealTotal`、`addRealNG`、`addTypeTotal`、`addDefectNG`
- `setCamMultiRoad`、`setCamMultiTotal`、`setCamMultiNgTotal`

**队列 / 状态（加锁）**

- `getDetailQueue`：`swap(NgDetails)`
- `saveProductData`
- `dealRecheckResultData`、`clearRecheckData`、`tryDequeueRecheckResult`
- `getCameraAlgorithm`、`clearCameraAlgorithm`
- `updateCameraDetectStatus`、`getCameraDetectStatus`（含索引边界检查）
- `ResetLed`、`ResetMergeData`

#### `Qt_Vision.cpp`

```cpp
int maxSpeed = -1;
if (!globalVariant.Speeds.isEmpty()) {
    maxSpeed = *std::max_element(...);
}
ProductDataHelper::GetInstance()->saveProductData(maxSpeed);
// ...
if (maxSpeed >= 0) {
    Adapter::getInstance()->setSpeed(maxSpeed);
}
```

- 修复空 `Speeds` 解引用 UB。
- 修复编译错误：原 632 行 `*_maxSpeed` 改为 `maxSpeed`。

#### `QtRecheckWidget.cpp`

- 禁止直接访问 `recheckResults`。
- 改为 `tryDequeueRecheckResult(result)`。

## 4. UI / 性能影响评估

| 场景 | 影响 | 说明 |
|------|------|------|
| 右侧生产数据 200ms 刷新（`getTotal`×N） | **极低** | 单次读锁微秒级 |
| 相机画面区 1s 刷新 | **极低** | 同上 |
| 复检界面 20ms `tryDequeue` | **极低** | 单条 dequeue |
| 每 5s `saveFileData` → `xlsx.save` | **中** | 耗在 GUI 线程 xlsx/IO，**不在 dataLock 内** |
| 每 5s `saveProductData` → `saveSelf` | **中** | **持锁 + 磁盘写**；可能阻塞 `MainThread` 计数；加锁前也会在 GUI 写盘 |

**结论**：加锁本身对日常刷新 **影响不大**；若仍有周期性卡顿，优先排查 **`saveProductData` / `saveFileData` 在 GUI 线程做 IO**，而非读锁。

**后续可选优化**（未实施）：

1. `saveProductData`：锁内只更新内存，**释放锁后再 `saveSelf()`**。
2. 定时存盘任务投递到工作线程。
3. 提供 `snapshotProductCounts()` 减少 UI 多次进出锁（收益小）。

## 8. 结论

1. **本次崩溃** 表现为 `LocalFile::saveProductCsvFile` → `xlsx.save()` 内 `QString` 释放失败，根因是 **`ProductDataHelper` 生产数据在多线程间无锁读写 `QVariantMap` / `QQueue`**。
2. **修复核心**：`QRecursiveMutex dataLock` + 读写对称加锁 + 复检队列封装 + 相关辅助数据加锁。
3. **对 UI**：读锁开销可忽略；需关注 **5s 周期 GUI 写盘** 的既有瓶颈，必要时将 IO 移出锁或移出主线程。
4. 若仍出现 `0xC0000374`，需继续按堆栈分流排查（参数导出、Adapter 等其它路径）。
