# 复检 map 快照无锁读与延迟回收方案

> 创建日期：2026-08-03
> 主题：消除 `__mapName2Algs` 实时路径每帧加锁；在线增删工具时对象生命周期安全回收
> 关联文档：`2605复检异常问题排查与修复汇总.md`（#3 map 并发、#6 延后删除、#7 野指针）
> 涉及文件：`XZJVisionDemoTool/Adapter/adapter.cpp`、`adapter.h`、`Qt_Vision/FlowThread.cpp`、`Qt_Vision/MainThread.cpp`、消费端工具

---

## 1. 背景与目标

### 1.1 问题来源

排查文档 #3 指出 `__mapName2Algs`（`QMap<QString, BaseTool*>`，红黑树）在检测线程无锁遍历 + 主线程增删节点时迭代器失效，导致 `0xC0000374` 堆损坏（压测约 8h 一次）。已用 `mutexAlgMap` + `getAlgMapCopy()` 缓解，但带来新问题：

- **实时路径每帧抢锁**：`FlowThread` / `MainThread` 每帧调用 `getAlgMapCopy()`（持 `mutexAlgMap`），与主线程 `deleteTool` / `__generateTool` / `applyRecheck` 竞争同一把锁，阻塞检测。
- **在线增删的对象生命周期竞态未根治**：`applyRecheck` 本身就是在线增删实时相机工具，文档 #6 的"旧帧 process + OutPut 判可删"过渡竞态仍存在。

### 1.2 目标

- **读端无锁**：检测线程每帧获取跨相机全量工具数据，不抢 `mutexAlgMap`。
- **删端安全**：`deleteTool` 锁内只做 `map.remove` + 入队，`delete` 推迟到"确认无检测线程引用"的安全点。
- **保持原功能**：`rtFlow.flowApplicationContext.mAlgMap` 依旧是 `QMap<QString, BaseTool*>` 值类型，含跨相机所有工具，消费端接口不变。

## 2. 现状分析

### 2.1 mutexAlgMap 能否去掉 —— 不能

`__mapName2Algs` 是 QMap（红黑树）。检测线程遍历 vs 主线程增删节点，结构性并发必须互斥，否则迭代器失效 -> UAF -> `0xC0000374`。"只读旧 key、只写新 key"也不安全（插入新节点仍改变遍历路径）。

**但 mutexAlgMap 是结构锁，不是生命周期锁**：

- 只保证"锁内查表得到的指针此刻在 map 中"。
- 不保证指针指向对象在锁外仍存活——检测线程 `process` 体内不持锁，`deleteTool` 锁内 `delete` 后，已拿到指针的检测线程仍 UAF。
- 管不到锁外缓存的指针（UI `bastTools`、`AlgorithmToolHelper` 快照 `AlgoImpl`、`ParameterExportTable`）。

### 2.2 QMap 隐式共享 —— "整表拷贝"的真实来源被误判

`QMap` 是 implicit-shared。当前代码：

- `getAlgMapCopy()` 内 `return __mapName2Algs;` —— **浅拷贝 O(1)**，不是红黑树深拷贝。
- `rtFlow.mAlgMap = getAlgMapCopy();` —— **浅拷贝 O(1)**。

所以"整表拷贝"并非 `getAlgMapCopy` 本身造成。真实开销有二：

| 开销 | 来源 |
|------|------|
| 每帧抢 `mutexAlgMap` | `getAlgMapCopy` 必须持锁读 map，多相机每帧与业务写竞争，阻塞实时路径 |
| 消费端 detach 深拷贝 | `xzjconditioncomparetool.cpp:281` 的 `data->mAlgMap.begin()` 在非 const QMap 上调用 non-const `begin()`，触发 detach（共享数据深拷贝），每个条件比较工具每帧一次 |

### 2.3 applyRecheck 在线增删场景

产线在检测中，`applyRecheck`（`adapter.cpp:3263`，全程持 `mutexAlgMap`）对实时工具 map 做三类操作：

| 操作 | 代码位置 | 快照方案表现 | 对象存活由谁保证 |
|------|----------|--------------|------------------|
| 新增（复检相机新加的工具） | 3415 `__mapName2Algs[_realCamToolName] = _realToolPtr;` | 晚一帧生效，安全 | 新对象未被引用，天然安全 |
| 改参（复检相机改了参数的同名工具） | 3388 `setValueFromOtherTool2` + `saveSelf` + `onLoadParams(true)` | map 不变不 publish，本帧即生效（同一指针） | 无对象存活问题，但有**对象内部数据竞争**（既有，非本方案范围） |
| 删除（复检相机删掉的真实工具） | 记 `_MapCamDelayDelteTools`，延后 `checkWhethreDeleteDelay` -> `deleteTool` | 旧快照仍含指针 | **延后删除闸门 + version 闸门**（本方案阶段 2） |

> 注："增删工具时停检"的产线约定在 `applyRecheck` 场景**不成立**——`applyRecheck` 本身就是在线增删，产线不会为此停检。

## 3. 总体架构

```
读端(检测线程)          写端(主线程/OutPutThread)        回收(OutPutThread)
  │                        │                              │
  帧: load ver ──┐         deleteTool:                    tryReclaim:
  取 shared_ptr  │          锁内 take+文件删+widget清理    锁内算 minActiveVer
  store(activeVer=v)        publish(version->V_new)        收集 V_remove<=min 的项
  process 全程持 v          入队{tool, V_new}              释锁
  store(activeVer=0) ───────┼──────────────────────────────┼──> 锁外 onToolDeleteAction+delete
                            │                              │
            version 序列统一驱动读快照选择 与 删除安全判定
```

两个关键不变量：

1. **读无锁**：检测线程通过 `shared_ptr<const QMap>` + version 短路拿快照，全程不抢 `mutexAlgMap`。
2. **删延后**：`deleteTool` 锁内只 `take` + `publish` + 入队；`delete` 推迟到"所有活跃读线程的 `activeVer >= V_new`"（即没人还持有含该工具的旧快照）。

## 4. 阶段 1：shared_ptr 快照 + version 短路（去每帧锁）

> 单独可落地，低风险，立即拿到"每帧零锁零深拷贝"。不改变对象生命周期，行为与现状等价。

### 4.1 Adapter 新增成员

`adapter.h`：

```cpp
#include <memory>
#include <atomic>
private:
    std::shared_ptr<const QMap<QString, BaseTool*>> __algMapSnap;
    std::atomic<uint64_t> __algMapVer{0};
    void __publishAlgMapSnap();   // 必须已持 mutexAlgMap
public:
    std::shared_ptr<const QMap<QString, BaseTool*>> getAlgMapSnap() const;
    uint64_t algMapVerAcquire() const { return __algMapVer.load(std::memory_order_acquire); }
```

### 4.2 发布与获取

`adapter.cpp`：

```cpp
void Adapter::__publishAlgMapSnap()
{
    // 调用方已持 mutexAlgMap
    // make_shared 拷贝构造 QMap 是浅拷贝 O(1)；之后 __mapName2Algs 再改会 detach 到新 d，本快照不受影响
    auto p = std::make_shared<const QMap<QString, BaseTool*>>(__mapName2Algs);
    std::atomic_store(&__algMapSnap, p);
    __algMapVer.fetch_add(1, std::memory_order_release);
}

std::shared_ptr<const QMap<QString, BaseTool*>> Adapter::getAlgMapSnap() const
{
    return std::atomic_load(&__algMapSnap);   // 无 mutexAlgMap 锁
}
```

构造函数末尾（首次填充 `__mapName2Algs` 后）调用一次 `__publishAlgMapSnap()` 初始化。

### 4.3 写入口：改完 map 必须发布

以下位置都在 `mutexAlgMap` 锁内，改完 `__mapName2Algs` 后补 `__publishAlgMapSnap();`：

| 位置 | 操作 |
|------|------|
| `__generateTool` 1693 `__mapName2Algs[toolName] = _algImpl;` 之后、return 前 | 新增工具 |
| `deleteTool` 主路径 + 3 个 catch 分支 `remove` 之后 | 删除工具 |
| `applyRecheck` 3415 `__mapName2Algs[_realCamToolName] = _realToolPtr;` 之后 | 应用复检新增 |
| `applySpec` 361、2202 `clear()` 之后 + `__restore` 完成 | 规格切换 |
| 2221 `remove` 之后 | 其它删除 |

> 强烈建议把 `__mapName2Algs` 写入收敛到私有 helper（`__setTool`/`__removeTool`/`__clearTools`），helper 末尾自动 publish，避免漏点。

### 4.4 读端：version 短路，每帧零锁零深拷贝

`rtFlow` 每帧新建，缓存放 `FlowThread` / `MainThread` 成员（线程局部，跨帧保持）：

```cpp
// FlowThread.h 成员
std::shared_ptr<const QMap<QString, BaseTool*>> m_cachedSnap;
uint64_t m_cachedVer = 0;

// run() 每帧，替换原 getAlgMapCopy() 那行
auto v = Adapter::getInstance()->algMapVerAcquire();          // 一次 atomic 读，无锁
if (v != m_cachedVer || !m_cachedSnap) {
    m_cachedSnap = Adapter::getInstance()->getAlgMapSnap();   // 仅 map 变更帧才 atomic_load
    m_cachedVer  = v;
}
rtFlow.flowApplicationContext.mAlgMap = *m_cachedSnap;        // QMap 浅拷贝 O(1)，含跨相机全量
```

`MainThread.cpp:704` 同样改造。`getAlgMapCopy()` 保留兼容，内部可改为 `return __algMapSnap ? *getAlgMapSnap() : QMap<QString,BaseTool*>();`，也变锁无关。

效果：工具 map 不变时（99.9% 的帧），每帧只有一次 `atomic<uint64_t>` 读 + 一次 QMap 浅拷贝，**零 `mutexAlgMap`、零 `atomic_load<shared_ptr>`、零深拷贝**。

### 4.5 消费端：const 遍历，去掉 detach

`xzjconditioncomparetool.cpp:281`：

```cpp
const auto& algMap = data->mAlgMap;                          // 强制 const 视图
for (auto it = algMap.constBegin(); it != algMap.constEnd(); ++it) { ... }
// 或 for (auto it = std::as_const(data->mAlgMap).begin(); ...
```

`xzjdatastoragetool.cpp:172/181`、`xzjprotocolsplicingtool.cpp:137/146` 用 `keys()`/`values()`（const，不 detach），但遍历两遍 + 构造两个 QList，可顺手改一次 `constBegin/constEnd` 遍历。

> 任何 non-const 方法（`begin()`/`operator[]`/`insert`）都会 detach，前功尽弃。消费端统一 const 访问。

## 5. 阶段 2：延迟回收队列 + version 闸门（根治在线删除竞态）

> 把"同步 delete"换成"移出 map + 安全点回收"，根治文档 #6 残留竞态，并把 `delete`/`onToolDeleteAction` 移出锁临界区。

### 5.1 新增数据结构

`adapter.h`：

```cpp
struct PendingDeleteTool {
    BaseTool*  tool = nullptr;
    uint64_t   removedSnapVer = 0;   // 删除后发布的新快照 version（含它的最后快照 = removedSnapVer-1）
};
private:
    QList<PendingDeleteTool>            __pendingDeleteTools;   // mutexAlgMap 保护
    QVector<std::atomic<uint64_t>*>     __readerActiveVers;     // 注册的读线程 activeVer 槽
    void __tryReclaimPendingTools();   // 内部加锁，delete 移锁外
public:
    int  registerReaderThread(std::atomic<uint64_t>* av);   // 返回槽位
    void unregisterReaderThread(int slot);
```

### 5.2 读端：注册 + activeVer 声明

注册时机：线程构造时 `registerReaderThread(&m_activeVer)`，析构时 `unregisterReaderThread`。

```cpp
// FlowThread.h
std::shared_ptr<const QMap<QString, BaseTool*>> m_cachedSnap;
uint64_t m_cachedVer = 0;
std::atomic<uint64_t> m_activeVer{0};   // 0=帧外空闲，>0=帧内持有该 version 快照
int      m_readerSlot = -1;

// run() 每帧
auto v = Adapter::getInstance()->algMapVerAcquire();          // atomic load，无锁
if (v != m_cachedVer || !m_cachedSnap) {
    m_cachedSnap = Adapter::getInstance()->getAlgMapSnap();   // 仅变更帧 atomic_load
    m_cachedVer  = v;
}
m_activeVer.store(m_cachedVer, std::memory_order_release);    // 进帧声明
rtFlow.flowApplicationContext.mAlgMap = *m_cachedSnap;        // QMap 浅拷贝 O(1)
// ... 全流程 process（全程持有 m_cachedVer）...
m_activeVer.store(0, std::memory_order_release);              // 出帧声明
```

`m_activeVer` 语义：非 0 即"本线程正在用 version=v 的快照跑 process"。回收线程据此知道还有谁停留在哪个代。

### 5.3 deleteTool 改造

锁内只做 map 变更 + 资源解绑 + 入队，`delete` 与 `onToolDeleteAction` 移到回收点：

```cpp
bool Adapter::deleteTool(QString toolName, bool recheck)
{
    {
        QMutexLocker locker(&mutexAlgMap);
        // ... recheck 前缀处理、contains 检查 ...
        auto algImp = __mapName2Algs.take(toolName);   // 取出并 remove
        if (!algImp) return false;

        // 状态闸门保留（与 checkWhethreDeleteDelay 协同）
        if (algImp->getDetectStatus() || algImp->getInitStatus() || algImp->getParamReadingStatus()) {
            __mapName2Algs[toolName] = algImp;   // 放回，拒绝删除
            return false;
        }

        // 立即做：与对象生命无关的清理
        QFile _file(algImp->getFilePath());
        if (_file.exists()) _file.remove();
        for (auto it = __mapName2Widgets.begin(); it != __mapName2Widgets.end(); ++it)
            if (it.value() && it.value()->getAlgPtr() == algImp)
                it.value()->clearAlgPtr();        // widget 立即解绑，避免再访问

        // 发布新快照，version -> V_new
        __publishAlgMapSnap();
        uint64_t vNew = __algMapVer.load(std::memory_order_relaxed);

        // 入待删队列，不 delete
        __pendingDeleteTools.push_back({algImp, vNew});
    }
    // 锁外尝试回收（回收判定在锁内，delete 在锁外）
    __tryReclaimPendingTools();
    return true;
}
```

> 原 `catch` 分支的"delete 前抛异常导致悬空留在 map"旧隐患（文档 #1）一并消除：统一走 `take` + 入队。

### 5.4 安全点回收逻辑（核心）

```cpp
void Adapter::__tryReclaimPendingTools()
{
    QList<BaseTool*> toDelete;
    {
        QMutexLocker locker(&mutexAlgMap);
        uint64_t minActiveVer = UINT64_MAX;
        bool anyReader = false;
        for (auto* av : __readerActiveVers) {
            if (!av) continue;
            uint64_t v = av->load(std::memory_order_acquire);
            if (v != 0) { anyReader = true; minActiveVer = std::min(minActiveVer, v); }
        }
        // 安全条件：含该工具的最后快照(removedSnapVer-1) 不被任何活跃读线程持有
        //          即 minActiveVer >= removedSnapVer（或无活跃读线程）
        for (auto it = __pendingDeleteTools.begin(); it != __pendingDeleteTools.end(); ) {
            if (!anyReader || minActiveVer >= it->removedSnapVer) {
                toDelete.append(it->tool);
                it = __pendingDeleteTools.erase(it);
            } else {
                ++it;
            }
        }
    }
    // 锁外执行耗时回收：模型释放、析构，不阻塞写端抢锁
    for (auto* t : toDelete) {
        try { t->onToolDeleteAction(); } catch (...) { /* 原有日志 */ }
        delete t;
    }
}
```

**为什么能根治文档 #6 残留竞态**：原 `checkWhethreDeleteDelay` 只看 `toolsCheck` + `bDetecting`，有"OutPut 判可删的帧 vs 检测线程用旧快照开跑的下一帧"窗口。现在即使 `toolsCheck` 不含、`bDetecting` 为 false，只要还有读线程 `activeVer < V_new`（仍持有含该工具的旧快照），`minActiveVer >= removedSnapVer` 不成立，**不 delete**。version 闸门把"检查-执行"窗口彻底闭合。

### 5.5 回收触发时机

1. `deleteTool` 入队后调一次（多数情况下读线程早已推进，能立即回收）。
2. **`OutPutThread` 每帧收尾调一次**（最自然，OutPutThread 已驱动 `checkWhethreDeleteDelay`，顺带 `__tryReclaimPendingTools`）。读线程 `activeVer` 置 0 后，下一轮 OutPutThread 回收就能判定通过。
3. 不要让检测线程自己同步调回收（会让检测线程等 `delete`）。

## 6. 与现有机制衔接

### 6.1 checkWhethreDeleteDelay

职责不变（判 `toolsCheck` 不含 + 空闲 -> 决定"该删谁"），但它调用的 `deleteTool` 现在变成"remove + 入队 + publish"，不再同步 delete。真正 delete 交给 `__tryReclaimPendingTools` 的 version 闸门：

```
checkWhethreDeleteDelay(判该删) -> deleteTool(移出map+入队) -> tryReclaim(version闸门通过才delete)
```

`bDetecting`/`bIsInit`/`bParamReading` 状态闸门**保留**作为快速路径（忙则连入队都不做，直接等下一轮），version 闸门作为最终安全保证。

> 注意：现有 `checkWhethreDeleteDelay`（`adapter.cpp:3594`）只查 `getDetectStatus() || getInitStatus()`，缺 `getParamReadingStatus()`，与 `deleteTool` 三项检查不一致。应统一为三项，或抽取 `canDeleteNow(toolName)` 谓词共用。

### 6.2 tryAcquireToolForParamRead / bParamReading

参数导出（文档 #9）已用 `tryAcquireToolForParamRead` + `bParamReading` 解决，正解保留。本方案的 version 闸门与 `bParamReading` 正交：参数读取走 acquire/release，删除走 version 闸门，互不干扰。

### 6.3 getAlgMap() 裸指针残留

`getAlgMap()` 仍返回 `&__mapName2Algs`（锁即释放），`QtAlgoFlowTree.cpp:2246` 还有 `getAlgMap()->contains()` 锁外使用（文档 #3 禁止模式）。应删除 `getAlgMap()` 或改私有，提供锁内 `containsTool(id)` / `peekTool(id)`，残留调用全部迁到 `getAlgMapCopy()` 或新接口。

## 7. applyRecheck 在线增删的覆盖

| 操作 | 行为 | 安全性 |
|------|------|--------|
| 新增（3415） | publish，读端下一帧 activeVer 推进后看到 | 天然安全 |
| 改参（setValueFromOtherTool2） | map 不变，不 publish；对象内部与 process 的成员级竞争**仍在**（既有，非本方案范围） | 不恶化也不解决 |
| 删除（延后） | checkWhethreDeleteDelay -> deleteTool(入队) -> tryReclaim(version 闸门) | **根治文档 #6 残留竞态** |

**改参的对象内部数据竞争**说明：`setValueFromOtherTool2` 在主线程持 `mutexAlgMap` 改对象成员，检测线程 `process` 不持锁读这些成员，存在读到半新半旧参数的竞态。这与 map 快照方案正交，当前代码即有，换不换快照都存在。工程上通常接受 `applyRecheck` 改参瞬间的瞬态不一致（产线预期"下一帧起生效"）；若产线对"改参当帧"敏感，才需引入对象级读写保护，单独立项。

## 8. 风险与阶段化建议

### 8.1 阶段化

- **阶段 1（必做，低风险，单独可拿收益）**：只上 shared_ptr 快照 + version 短路，`deleteTool` 保持现有同步 delete + `checkWhethreDeleteDelay`。立即拿到"每帧零锁零深拷贝"。不改变对象生命周期，行为与现状等价。
- **阶段 2（根治在线删除竞态）**：上延迟回收队列 + version 闸门。改动集中在 `deleteTool` 拆分 + `__tryReclaimPendingTools` + 读线程注册 `activeVer`。消除文档 #6 残留竞态，并把 `delete`/`onToolDeleteAction` 移出锁临界区（缩短 `mutexAlgMap` 持锁时间）。

### 8.2 风险点

| 风险 | 应对 |
|------|------|
| 读线程注册/注销必须配对 | FlowThread/MainThread 析构时注销，注册返回 slot，注销时置 `nullptr`，回收循环跳过 `nullptr` |
| `onToolDeleteAction` 延迟到回收点 | 若有"立即生效"副作用（如通知外部），需确认延迟可接受；不可则拆"立即部分（锁内）+ 延迟部分（回收点）" |
| 待删队列无界增长 | 某读线程长时间不推进 `activeVer`（卡死）会堆积。加上限告警 + 超时强制回收（带风险，仅兜底） |
| `std::atomic_load(shared_ptr)` 内部轻量锁 | C++17 全局 spinlock；阶段 1 version 短路已让它低频，阶段 2 不新增该调用 |
| 读端拿"略旧"快照 | 新增工具晚一帧生效（可接受）；删除工具靠 version 闸门 + 延后删除保证对象存活 |

### 8.3 边界

- 读端可能拿到"略旧"快照（增删工具后未及时反映）。旧快照只影响"哪些工具可见"，**不影响对象存活**——对象存活由 version 闸门 + 延后删除保证。
- publish 必须覆盖所有写入口，漏一个则读端拿陈旧 map。建议写入收敛到私有 helper，helper 末尾自动 publish（或 RAII 守卫，锁释放时 publish）。
- 消费端不要修改 `mAlgMap`，任何 non-const 方法都会 detach。

## 10. 一句话总结

阶段 1 用 `shared_ptr<const QMap>` 原子发布 + version 短路换掉"每帧抢锁"和"消费端 detach"；阶段 2 用 version 闸门 + 待删队列把"同步 delete"换成"移出 map + 安全点回收"。两者共用 version 序列，既拿到无锁读，又根治在线删除的对象生命周期竞态。`mAlgMap` 类型与跨相机全量语义都不变，消费端仅 `begin()` -> `constBegin()` 适配。
